# Audit complet — Junon (time-serie-explo)

Cet audit couvre le backend FastAPI (`api/`), les utilitaires dashboard (`dashboard/`), le frontend React/TypeScript (`frontend/src/`), l'infrastructure Docker/nginx et la gestion des dépendances. 41 constats ont survécu à la vérification contradictoire. Aucun constat n'est de sévérité critique, mais quatre défauts de sévérité haute touchent des invariants majeurs du projet : verrouillage administratif définitif, corruption silencieuse de la classification IPS scientifique, non-annulation d'un entraînement GPU partagé, et une explication SHAP « réussie » entièrement à zéro. Les thèmes récurrents sont la sécurité des accès (fail-open, exposition d'infra sans auth), la cohérence scientifique WMO/ERA5 (doublons de coordonnées flottantes, désalignement date/valeur), et la cohérence linguistique FR (franglais résiduel non passé par i18n).

**Statistiques** — Total : 41 constats. Par sévérité : 4 hautes, 17 moyennes, 20 basses. Par catégorie : bug 12, quality 10, security 7, data-coherence 6, perf 6.

## admin — Gestion des utilisateurs

### [HAUTE] update_user peut retirer le dernier admin et provoquer un verrouillage définitif
- **fichier** : api/routers/admin.py:56
- **description** : `delete_user` (l.109-118) refuse de supprimer le dernier admin, mais `update_user` n'a aucune garde équivalente. Un admin peut positionner `role=user` (l.63-65) ou `is_active=False` (l.60-62) sur l'unique compte admin (y compris le sien) ; chaque chemin incrémente `token_version` et invalide la session immédiatement. L'invariant « au moins un admin » est appliqué de façon incohérente entre les deux chemins de mutation.
- **scénario de défaillance** : Déploiement mono-admin. L'admin envoie `PATCH /api/v1/admin/users/{own_id}` avec `{"role":"user"}`. Le serveur accepte, bump `token_version`, la requête suivante renvoie 401 ; il ne reste 0 admin actif. Tout endpoint admin renvoie 403/401 en permanence — récupération uniquement par édition DB manuelle ou `scripts/create_admin.py`.
- **correctif proposé** : Avant de committer une rétrogradation/désactivation dans `update_user`, si la cible est admin et que le changement ramènerait le nombre d'admins actifs à 0, compter les admins restants et lever un HTTP 409 (réutiliser la garde de `delete_user`). Interdire aussi à un admin de se rétrograder/désactiver lui-même.
- **verdict** : CONFIRMED — confiance haute.

### [MOYENNE] delete_user efface les artefacts de façon irréversible avant le commit DB
- **fichier** : api/routers/admin.py:120
- **description** : `erase_user_artifacts(uid)` (l.120) supprime définitivement les répertoires de datasets (`shutil.rmtree`) et les runs MLflow AVANT `db.delete(user)` et `db.commit()` (l.121-127). L'effacement n'est pas dans la transaction et n'est pas rejoué.
- **scénario de défaillance** : Admin supprime X. `erase_user_artifacts` efface les datasets/runs de X. `db.commit()` échoue (reset connexion) → l'API renvoie 500, X existe toujours en compte actif, mais ses modèles/datasets sont définitivement détruits et aucun événement `admin_user_deleted` n'est persisté (rollbacké).
- **correctif proposé** : Réordonner : committer d'abord la suppression DB + l'événement d'audit, puis invoquer `erase_user_artifacts` en best-effort après commit (ou en tâche post-commit indexée par user_id).
- **verdict** : CONFIRMED — confiance moyenne.

### [BASSE] create_admin.py accepte le mot de passe admin en argument CLI
- **fichier** : scripts/create_admin.py:19
- **description** : L'option `--password` permet de passer le credential admin sur la ligne de commande. Sur un hôte partagé, la valeur est visible via `ps`/`/proc/<pid>/cmdline` pendant l'exécution et est écrite dans l'historique du shell. Un chemin getpass sécurisé existe déjà quand `--password` est omis.
- **scénario de défaillance** : `python scripts/create_admin.py --email a@b.fr --name X --password S3cret!` dans le conteneur → un autre utilisateur exécute `ps aux ww` et capture le mot de passe ; il persiste aussi dans `~/.bash_history`.
- **correctif proposé** : Supprimer `--password` (ou n'accepter le secret que via variable d'environnement/stdin) et toujours utiliser getpass ; si conservé pour l'automatisation, documenter qu'il doit venir d'un fichier/env, jamais d'un littéral inline.
- **verdict** : CONFIRMED — confiance moyenne.

## cf-xai — Explicabilité et contrefactuels

### [HAUTE] SHAP renvoie success=True même quand le wrapper échoue et retourne des attributions nulles
- **fichier** : api/routers/explainability.py:267
- **description** : Dans `shap_analysis`, le `model_wrapper` enveloppe `model.predict` dans un `except Exception: return np.zeros(...)`. Le fallback de perturbation calcule l'importance comme `(baseline_pred - perturbed_pred)` ; si tout `predict` lève (ex. modèle Darts exigeant `future_covariates` non fournies), toutes les importances valent 0.0 et l'endpoint (l.282-288) fixe inconditionnellement `success=True`.
- **scénario de défaillance** : Modèle TFT/transformer nécessitant `future_covariates` → chaque `predict` lève → wrapper renvoie des zéros → `POST /shap` renvoie 200 `{success:true, feature_importance: tout à 0}`, présentant une explication scientifiquement vide comme un succès.
- **correctif proposé** : Faire propager les échecs du `model_wrapper` (compteur d'exceptions) et faire renvoyer à `compute_shap_importance`/`shap_analysis` `success=False` + message d'erreur quand le wrapper n'a jamais produit de prédiction valide, au lieu de substituer des zéros.
- **verdict** : CONFIRMED — confiance moyenne.

### [MOYENNE] lag_importance et seasonality_analysis désérialisent le modèle torch sans l'utiliser
- **fichier** : api/routers/explainability.py:368
- **description** : Les deux endpoints GET appellent `_load_model_for_explain(model_id)` qui exécute `registry.load_model(entry)` (checkpoint TFT/Transformer complet, `force_cpu_if_needed`, scalers) à chaque requête. Ni `model` ni `scalers` ne sont ensuite référencés : `lag_importance` n'a besoin que de la colonne cible (ACF/PACF), `seasonality_analysis` que du dataframe (FFT/STL).
- **scénario de défaillance** : Un dashboard appelant `/{model_id}/seasonality` et `/{model_id}/lag-importance` pour plusieurs stations déclenche un chargement de poids TFT multi-Mo + déplacement CPU par requête, ajoutant des secondes de latence pour un calcul ne touchant qu'une Series pandas.
- **correctif proposé** : Ajouter un loader léger (ou un flag `load_model=False`) renvoyant seulement config/scalers/dataframes pour ces deux endpoints, en sautant `registry.load_model`.
- **verdict** : CONFIRMED — confiance haute.

### [BASSE] ips_reference charge la grille de référence puis la jette et re-requête la même table
- **fichier** : api/routers/counterfactual.py:610
- **description** : `ips_reference` appelle `_load_station_grid(...)` (l.610) — engine, connexion, SELECT sur `gold.station_reference_stats`, dispose — dont le résultat n'est jamais réutilisé. Immédiatement après (l.618-632), un second engine exécute quasiment le même SELECT.
- **scénario de défaillance** : Chaque `GET /ips-reference` fait 2× les allers-retours DB et 2× la création d'engine/pool ; un dashboard qui interroge par modèle double la charge DB inutilement.
- **correctif proposé** : Supprimer l'appel l.610 et dériver `n_years/mu/sigma` de la requête unique l.618-632 (ou étendre `_load_station_grid` pour renvoyer aussi `n_years`).
- **verdict** : CONFIRMED — confiance haute.

### [BASSE] Un nouvel engine SQLAlchemy est créé puis détruit à chaque lecture warehouse
- **fichier** : api/routers/counterfactual.py:56
- **description** : `_load_station_grid` (l.56), `ips_reference` (l.618) et `ips_bounds` appellent `create_engine(_brgm_url())` puis `engine.dispose()` par invocation, ce qui défait le pooling. `api/database.py:48-69` fournit pourtant `get_brgm_sync_engine()` module-level poolé, avec un commentaire explicite recommandant de le réutiliser.

- **correctif proposé** : Remplacer les `create_engine`/`dispose` par cellule par `api.database.get_brgm_sync_engine()` avec `with engine.connect()`.
- **verdict** : CONFIRMED — confiance moyenne.

## forecast-models — Entraînement et prévision

### [HAUTE] L'annulation d'un entraînement ne stoppe pas le GPU et laisse démarrer un second job
- **fichier** : api/routers/training.py:138
- **description** : Le thread ne vérifie `task.stop_event.is_set()` qu'une fois, l.138, AVANT `run_training_pipeline`. Le pipeline (l.166-192) ne reçoit ni `task`, ni `stop_event`, ni callback, donc la boucle d'entraînement ne peut plus être interrompue. `task_manager.cancel()` met status=CANCELLED aussitôt, et la garde de `start_training` (l.252-255) ne compte comme actifs que PENDING/RUNNING — un job annulé mais toujours en cours n'est plus compté.
- **scénario de défaillance** : A lance un NHiTS 200 époques, annule à l'époque 5. L'UI montre CANCELLED mais le thread continue les 200 époques sur la RTX A6000. B (ou A) lance `/training/start` : la garde ne trouve rien de PENDING/RUNNING → 2ᵉ entraînement concurrent → CUDA OOM. Violation de l'invariant « un seul entraînement à la fois ».
- **correctif proposé** : Passer `task.stop_event` à `run_training_pipeline` et sonder entre époques via un callback Lightning ; et/ou compter les tâches CANCELLED-mais-thread-vivant (`task.thread.is_alive()`) comme actives dans la garde.
- **verdict** : CONFIRMED — confiance haute.

### [MOYENNE] Le thread d'entraînement écrase inconditionnellement CANCELLED par COMPLETED
- **fichier** : api/routers/training.py:194
- **description** : Après retour de `run_training_pipeline`, le thread fait `with task.lock: task.status = COMPLETED` (l.194-201) sans vérifier une annulation entre-temps. Comme l'annulation ne stoppe pas le pipeline, un job annulé finit puis rétablit lui-même son status en COMPLETED et enregistre le run MLflow.
- **scénario de défaillance** : L'utilisateur annule (status CANCELLED, SSE « done » déjà émis) ; le pipeline finit quelques minutes plus tard, l.194 remet COMPLETED, les `results` sont stockés — contredisant l'annulation affichée.
- **correctif proposé** : Avant d'écrire le status terminal, re-vérifier sous verrou : `if task.stop_event.is_set() or task.status == CANCELLED: return` (et sauter l'enregistrement du run).
- **verdict** : CONFIRMED — confiance haute.

### [MOYENNE] Endpoints de prévision async exécutant du travail bloquant → event loop figé
- **fichier** : api/routers/forecasting.py:98
- **description** : Les quatre handlers sont `async def` (l.98, 172, 214, 256) mais font du travail lourd bloquant directement sur l'event loop sans `await`/`run_in_executor` : `_load_model_and_data` télécharge depuis MLflow et désérialise un modèle torch, puis inférence CPU/GPU. Aucun point de yield.
- **scénario de défaillance** : `/forecasting/rolling` sur un test set complet (plusieurs secondes d'inférence) fige tous les autres appels, y compris le flux SSE de métriques d'entraînement (`asyncio.sleep` l.318 dans training.py) et les health checks.
- **correctif proposé** : Déporter le chargement + inférence vers un threadpool (`anyio.to_thread.run_sync` / `run_in_threadpool`) ou déclarer les handlers en `def` simple.
- **verdict** : CONFIRMED — confiance moyenne.

## era5-situation — Observatoire ERA5

### [MOYENNE] La fenêtre observée SPI/précip fait un SUM brut, double-comptant les cellules doublons flottantes
- **fichier** : api/routers/observatory_era5.py:732
- **description** : Les requêtes de fenêtre observée pour le SPI (l.732 : `SUM(total_precipitation) ... GROUP BY round(latitude::numeric,1), round(longitude::numeric,1)`) et pour la branche précip de `/anomaly` (l.868) somment chaque ligne brute tombant dans une cellule 0.1°. Pour les cellules doublons ERA5 connues (même cellule physique sous deux coordonnées flottantes légèrement différentes), tout mois présent sous les deux variantes est compté deux fois. La référence gamma/climatologie évite ce double comptage via une moyenne pondérée par variante (l.513-524, 582-591, 292-302). Les deux chemins sont méthodologiquement incohérents.
- **scénario de défaillance** : Une cellule dont le dernier mois complet existe sous les deux variantes donne `window_sum ≈ 2×`. La CDF gamma à ~2× l'échelle renvoie ~1.0 → SPI plafonné à +3.09 → classé EXTREMEMENT_HAUT même un mois normal/sec ; `/anomaly` précip affiche ~+100 %.
- **correctif proposé** : Canoniser les doublons comme la référence : agréger d'abord par (lat brut, lon brut, mois) en SUM, puis fusionner les variantes 0.1° par moyenne pondérée par le compte avant d'accumuler la fenêtre N mois. Appliquer le même correctif à `/anomaly` (l.868).
- **verdict** : CONFIRMED — confiance moyenne.

### [BASSE] Le démarrage relance des scans de climatologie redondants avec les warmers STI/SPI
- **fichier** : api/routers/observatory_era5.py:216
- **description** : Au démarrage (main.py:94-97), quatre scans full-table de `gold.era5_grid` s'exécutent : `_era5_temp_climatology` (l.216), `_era5_precip_climatology` (l.268), `_warm_era5_sti_default` (l.647), `_warm_era5_spi_default` (l.672). Les warmers STI/SPI construisent déjà les moyennes/sommes par (cellule, année, mois) dans `by_cell` ; les climatologies (moyenne par mois calendaire) en sont dérivables.
- **scénario de défaillance** : Chaque cold start / refresh de cache paie ~2 scans full-table redondants relisant les mêmes colonnes température/précip sur une période chevauchante (contention I/O DB).
- **correctif proposé** : Dériver les climatologies température/précip des maps `by_cell` des warmers STI/SPI (en conservant les comptes par (année,mois) pour la pondération), en supprimant les deux scans autonomes.
- **verdict** : CONFIRMED — confiance basse.

## hydro-piezo — Débit / piézométrie

### [MOYENNE] La sous-requête LATERAL de get_station omet la borne basse QmnJ, laissant les sentinelles négatives polluer la médiane
- **fichier** : api/routers/observatory_hydro.py:595
- **description** : Les autres chemins de lecture filtrent les DEUX bornes sentinelles (`get_percentiles` l.184-185, `get_ssfi` l.380). Mais la LATERAL `lm` de `get_station` ne garde que la borne haute : l.595 `m2.resultat_moyen < 1e8` (pour `month_median`) et l.600 idem (pour `ref_value`). ## Thèmes transversaux

- **Sécurité des accès et fail-open** — Les contrôles d'authentification/abus dégradent silencieusement vers « aucune protection » : rate-limit/verrouillage fail-open sur panne Redis (`ratelimit.py`), logout sans révocation de jeton, énumération par timing (`auth.py`). Recommandation générale : fail-closed pour au moins un contrôle et adosser un compteur d'échecs à la DB.
- **Cohérence de l'invariant admin** — L'invariant « au moins un admin » n'est appliqué que dans `delete_user`, pas dans `update_user` (verrouillage définitif). Ordonnancement dangereux effacement/commit dans `delete_user`. Credential admin exposable en CLI.
- **Cohérence scientifique WMO / ERA5** — Deux familles de bugs de coherence des données : (1) doublons de coordonnées flottantes ERA5 non canonicalisés (`observatory_era5.py:732/868` SUM brut ; `station_loader.py:200` jointure par égalité flottante) ; (2) désalignement date/valeur et mois-de-référence (`CounterfactualPage.tsx:150` faussant les classes IPS ; `observatory_hydro.py:595` sentinelles négatives dans la médiane). Ces défauts corrompent silencieusement des indicateurs standardisés et le verdict de qualification.
- **Robustesse des tâches longues et pooling** — GPU partagé non protégé (annulation d'entraînement non propagée, status écrasé), endpoints async faisant du blocking, auto-fit synchrone sans annulation, engines SQLAlchemy recréés par requête, chargements de modèle inutiles. Motif : ne pas suivre le pattern `task_manager`/SSE/`stop_event` et `get_brgm_sync_engine()` déjà présents dans le repo.
- **Fuites de ressources / robustesse fichiers** — Fichiers temporaires non nettoyés sur chemins d'erreur ou de succès (`datasets.py:104`, `pastas.py:830`), cache WFS empoisonné 24h, crash `/snapshot` sur table vide, NaN sérialisé en JSON invalide.
- **Cohérence FR / no-franglais / i18n** — Libellés anglais codés en dur contournant `t()` dans plusieurs pages/composants (`PumpingDetectionPage`, `ForecastPlot`/`TestSetOverview`, `TopNav`), non traduits au changement de langue.
- **Config morte et dérive de dépendances** — Config Streamlit orpheline, effets de bord d'import CUDA, `MODEL_COLORS` incomplet, pins mlflow/torch contradictoires entre 4 sources et fichiers `requirements/*.txt` hérités non utilisés.
- **Invariant « no implicit filtering »** — La sélection d'une station modifie l'état global (efface le filtre spatial dans l'Observatoire), et l'affichage temporel est incohérent entre secteurs et marqueurs sur /meteo.
- **Durcissement infra HTTP** — La SPA et MLflow sont exposés en contournant/absentant les protections (reverse-proxy durci contourné, MLflow sans auth, en-têtes de sécurité perdus par héritage nginx).
