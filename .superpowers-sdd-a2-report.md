### 1. `/spi` et `/sti` → lecture directe `gold.fct_era5_indices_grid`

Plus de gamma-fit ni de z-score calculé côté API : la requête `SELECT era5_latitude,
era5_longitude, spi|sti FROM gold.fct_era5_indices_grid WHERE month=:m AND fenetre=:w`
est formatée par deux nouvelles fonctions pures testables sans DB
(`_rows_to_spi`/`_rows_to_sti` dans `observatory_era5.py`), qui arrondissent/classifient
via `classify_index` (réutilisé) — **shape de réponse identique**
(`[{latitude, longitude, spi|sti, index_class}]`), y compris le détail que `spi` est
arrondi à 3 décimales et `sti` ne l'est pas (comme avant).

Résolution du mois par défaut : nouvelle fonction `_resolve_indices_month` — `MAX(month)
FROM fct_era5_indices_grid WHERE fenetre=:w`, clampée si une date future/trop récente est
demandée (mirroring `_resolve_month_start`, mais scoping direct sur le mart au lieu de la
table journalière). Vérifié sur l'entrepôt réel : `MAX(month)` du mart = juin 2026 =
exactement le dernier mois complet calculé par l'ancienne logique sur `gold.era5_grid`
(juillet 2026 en cours au 2026-07-07).

### 2. `/monthly` → lecture directe `gold.fct_era5_monthly_grid`

Plus d'agrégation à la volée sur la table journalière. Point d'attention découvert en
vérifiant contre l'entrepôt réel : le champ historique `potential_evaporation` est une
**moyenne journalière négative** (convention brute ERA5, consommée telle quelle côté
front pour le bilan hydrique `total_precipitation + potential_evaporation`), alors que
`etp_totale` du mart est un **total mensuel positif**. Reconstruit avec
`-(etp_totale / nb_jours)` — vérifié bit-for-bit contre l'ancienne requête sur un mois
réel (Tours, mai 2026) : `-5.9177144881217711` (ancien) vs `-5.9177144881217711`
(reconstruit). `temperature_2m`/`total_precipitation` matchent aussi exactement
(`temperature_moyenne`/`precipitation_totale`).

### 3. `/snapshot` simplifié

Vérifié que `bronze.era5_france_timeseries` (vue `gold.era5_grid`) n'a **aucun doublon

GROUP BY round(...)` est donc devenue une opération identité, remplacée par une simple
projection avec arrondi défensif (pas de `GROUP BY`).

### 6. SPI station (`observatory_piezo.py` / `observatory_hydro.py`)

`/stations/{code}/spi` ne fait plus de fit gamma par station (`compute_spi` de
`dashboard/utils/drought.py`, retiré des imports) : nouvelle jointure
station → cellule mappée → marts :

```sql
SELECT m.mois, m.precipitation_totale AS value, g.spi
FROM gold.int_station_era5_mapping map          -- ou int_hydro_station_era5_mapping / code_station
JOIN gold.fct_era5_monthly_grid m
  ON m.era5_latitude = map.era5_latitude AND m.era5_longitude = map.era5_longitude
LEFT JOIN gold.fct_era5_indices_grid g
  ON g.era5_latitude = map.era5_latitude AND g.era5_longitude = map.era5_longitude
 AND g.month = m.mois AND g.fenetre = :window
WHERE map.code_bss = :code
ORDER BY m.mois
```

Nouveau paramètre `window` (défaut **1**, matching l'ancien comportement — le fit gamma
par station opérait sur les totaux mensuels bruts, pas une accumulation sur plusieurs
mois). Formatage extrait en fonction pure partagée `station_spi_rows` (nouvelle,
`api/era5_anomaly.py`), réutilisée à l'identique par les deux routers.

Shape de réponse (`{mois, value, spi, classification}`) **inchangée**. Les *valeurs*
changent légèrement pour les stations dont l'historique remonte avant les corrections
amont de coordonnées ERA5 (ex. `BSS004NKHH/X`, févr. 2025 : ancien `18.3065mm` vs
nouveau `45.0611mm` depuis le mart corrigé) — attendu et voulu : le mart est désormais
la source canonique, remplaçant l'ancienne agrégation station par station qui héritait
de l'imprécision pré-fix. Vérifié end-to-end sur l'entrepôt réel (piézo `BSS004NKHH/X`,
919 mois de jointure ; hydro `A021005050`, jointure correcte).

Le seuil `MIN_MONTHS=60` (5 ans mini pour un fit stable) de l'ancien
`compute_spi`/`_compute_gamma_index` **disparaît** : le SPI est désormais calculé sur la
référence climatologique complète du mart (1991-2020), indépendamment de la longueur de
l'historique de la station — amélioration attendue de la migration, pas une régression.

## Fix: revue A2

**Constat vérifié par le contrôleur contre l'entrepôt réel** : `gold.era5_grid`
est une vue sur `bronze.era5_france_timeseries` — et bronze contient toujours des
coordonnées flottantes non arrondies pour la fenêtre 2026-01-21→2026-05-01
(~1,16M lignes ; seule SILVER a été purgée/re-stagée par la remédiation amont
mentionnée dans les "Points d'attention" ci-dessus). Le merge pondéré de
coordonnées dupliquées supprimé par le commit 8231128 dans `/snapshot` était
donc **toujours nécessaire** pour toute date dans cette fenêtre (et
défensivement pour toute régression d'ingestion future) — l'hypothèse "upstream
propre" qui justifiait la suppression ne tenait que pour SILVER, pas pour
BRONZE dont `gold.era5_grid` dépend directement.

### Correctif

- Réintroduction du merge dans `api/routers/observatory_era5.py`, extrait en
  fonction pure `_rows_to_snapshot(rows)` (même style que `_rows_to_spi` /
  `_rows_to_sti` : logique testable sans toucher la DB). La requête SQL ne
  round/agrège plus — elle renvoie les lat/lon brutes, et le regroupement par
  cellule 0.1° + moyenne des 3 variables (en ignorant les NULL, comme
  `AVG()` SQL) se fait côté Python. Reproduit le comportement pré-8231128
  (`GROUP BY round(...) / AVG(...)`).
- Commentaire ajouté au-dessus de la requête et dans la docstring de
  `_rows_to_snapshot` expliquant le fait vérifié : la vue `gold.era5_grid` lit
  BRONZE, jamais purgé — coordonnées non arrondies subsistent (jan-avr 2026 et
  potentiellement régressions futures) ; le dedup reste obligatoire côté
  endpoint.

### Test de non-régression

`tests/test_era5_snapshot.py` (4 tests, aucune DB touchée, même convention que
`test_era5_spi.py`) :
- deux variantes flottantes de la même cellule (`47.09999999999994` /
  `47.1`) fusionnées en une seule cellule avec moyenne des 3 variables ;
- cellules distinctes non fusionnées ;
- valeurs NULL ignorées dans la moyenne (comme `AVG()` SQL) ;
- variable entièrement NULL → reste `None` en sortie.
